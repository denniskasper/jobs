# Decision log

Every decision settled in the shaping session, with the reasoning compressed. Written before any
implementation, so the spec and tickets inherit the *why*, not just the *what*.

Terminology follows [CONTEXT.md](../CONTEXT.md). Three decisions were significant enough to get their
own ADR and are marked below.

## Shape and scope

| # | Decision | Reasoning |
|---|---|---|
| 1 | Public engine repo + private data repo, but **build private first** and extract later | Designing for open source on day one costs a config layer, docs and anonymised fixtures before a single application has been sent. Keep a hard seam between machinery and personal data; extract once it has actually run for a few months. |
| 2 | Build a **thin vertical slice**, not layer by layer | A slice from Source to rendered dashboard exercises every seam in a weekend. Layer-by-layer means nothing works end to end for months. |
| 3 | Two gates; the system **never sends** — *see [ADR 0001](adr/0001-two-gates-never-auto-submit.md)* | Auto-submission is unrecoverable, unreliable against real portals, and in the same ToS territory as scraping. |
| 4 | Unsolicited applications are **first class**: a Source can propose an approach to named contacts when nothing is advertised | Already part of the existing practice (boards-and-more, TUHH). Fits the model as a Posting with no URL. |
| 5 | The system **stops at Submission**, plus deadline awareness | Deadlines come free from JSON-LD `validThrough`. Interview prep stays a markdown file in the Application folder; wrapping it in UI adds structure to something that benefits from none. |
| 6 | Not in scope: hunting for companies worth an unsolicited approach | The value of an initiative application is that *you* have a reason to want that employer. An agent guessing produces the generic letter that gets deleted. |

## Data

| # | Decision | Reasoning |
|---|---|---|
| 7 | Files are the database — *see [ADR 0002](adr/0002-files-as-database.md)* | Folder-per-application already worked; survives neglect; fixable in an editor. A database buys queries nobody is asking at this scale. |
| 8 | Shared Documents content-addressed; Packets freeze into a Manifest at Submission | 628 PDFs, 320 MB, only 159 unique. A hash is stronger provenance than a copy, because a copy can be edited afterwards. |
| 9 | A **private git repo** (`jobs-data`) is the transport; Dropbox is retired. On the server it is a clone living inside the Dokploy **volume** mounted at `DATA_DIR` | History, sync, conflict detection and backup for free. Dropbox silently resolves concurrent writes, which is exactly wrong when an agent and a human both write; git stores symlinks natively, Dropbox re-copies them. The volume alone would not be enough: unlike a regenerable demo store, this data cannot be reseeded from anything, and a volume has no history and is not a backup. Git inside the volume supplies both. |
| 10 | Backup = three git clones (server volume, laptop, GitHub private); object-storage snapshots once the repo passes ~1 GB. The **server is the sole writer**; the laptop clone is pull-only | Losing the volume costs nothing but a `git clone` back to the last push. A single writer makes merge conflicts structurally impossible, which matters because interaction happens through the dashboard over Tailscale rather than by editing on two machines. Test the restore once. An untested backup isn't one. |
| 11 | Migration: backfill the 32 tracked Applications, freeze the older folders in a read-only `archive/` | The tracked ones carry status and rejection reasons — the corpus the relevance profile learns from. The rest predate the current approach. |
| 12 | Data repo is `jobs-data`; engine is `jobs`. The data store is **nested at `data/` inside the engine working tree and gitignored**, not a sibling directory | One working directory instead of two, following the arrangement already in use in `pdr.cloud`. Git never recurses into an ignored path, so the inner repo is invisible to the outer one and no submodule is involved. `data/` is also in `.dockerignore`, so no data ever enters the image. `jobs` is fine locally but a poor public repo name; rename at extraction time. |

## Discovery

| # | Decision | Reasoning |
|---|---|---|
| 13 | A Source is a **URL plus a frozen, editable config** — *see [ADR 0003](adr/0003-url-first-sources.md)* | Re-deriving structure per poll is slow, costly and non-deterministic. Derive once, then run as plain code. |
| 14 | Extraction prefers schema.org `JobPosting` JSON-LD, then selectors, then a model. Browser rendering is **not** a third extraction strategy but a concern of the fetch layer, applied when a static fetch yields no candidates | Google for Jobs makes JSON-LD near-universal on posting pages. Listing pages are the JS-rendered ones, and that is a question of how the bytes were obtained, not of how they are read. Keeping it at the fetch layer is what lets extraction stay pure and testable without a browser. |
| 15 | A Source returning zero Postings across consecutive runs is **flagged unhealthy** — a field on the Source, not a log line. Notifying about it is a later concern; being visible is not | Silent breakage is what kills scrapers, and a quiet Source looks exactly like a broken one until something distinguishes them. |
| 16 | Avoid LinkedIn, Indeed, StepStone, Xing, Glassdoor entirely | No public API; automated access explicitly prohibited. Wrapper libraries don't change that. |
| 17 | Bundesagentur `jobsuche` treated as off-limits for a stored pool | Their terms forbid automated collection and building your own job pool. A transient personal search is defensible; a database is not. |
| 18 | Relevance: rules first, then a model scores survivors against an explicit profile **and anti-profile** | A keyword filter cannot see the distinction the existing notes already draw — an engineering-and-integration role fitting well where a data-science role did not. |
| 19 | Every suggestion **shows its reason**, rejections stay inspectable, digest **capped at five per day** | A filter you can't audit is one you stop trusting, and then you read everything anyway. Uncapped digests get muted. |

## Interaction

| # | Decision | Reasoning |
|---|---|---|
| 20 | Pursue Gate is a **tick-list**, not a conversation; unticked Postings age out, on a clock that starts when a Posting is **first shown**, not when it is first found | Triage is a list operation. Telegram carries the same yes/no as a digest, so it clears from a phone. The first-shown clock exists because the daily cap and the age-out would otherwise fight: a Posting held back by the cap would expire without ever having been offered, and the record would call that neglect. Held-back Postings also outrank newly found ones, so a backlog drains rather than expiring from behind the queue. |
| 21 | Document revision happens in a **chat pane in the dashboard**, beside the rendered letter | Revising a letter is low-frequency and high-stakes; it needs to sit next to the Posting on a real screen. |
| 22 | Every agent edit is shown as a **diff** against what was last seen | An agent silently rewriting an approved letter is how a wrong figure reaches an employer. |
| 23 | Voice notes via Telegram drive **decisions**, not prose | "The Hamburg one, yes" is a fine voice input. Editing text you cannot see is not. |
| 24 | Email Submission produces an **`.eml` Draft**, never an SMTP send | The email analogue of leaving the submit button alone. Zero OAuth, opens in any client, and is its own archival record. |
| 25 | Inbox reading is **phase two**: read-only, restricted to senders already linked to an Application, and only ever *proposes* status changes | Highest-value remaining automation, but the biggest new trust surface. Misreading an interview invitation as a rejection corrupts the record silently — and the relevance profile then learns from the corrupted record. |

## Runtime and operations

| # | Decision | Reasoning |
|---|---|---|
| 26 | Everything runs on the dev server; nothing depends on the laptop being awake | Follows from unattended polling. |
| 27 | Server-rendered templates + HTMX; **keep the existing stylesheet verbatim** | One user, no offline need, data already server-side — an SPA buys a build step and state sync for nothing. The current design is good and already colour-validated; port the markup, not the look. |
| 28 | Python service, shelling out to ~~`md-to-pdf` and~~ `pdfunite` — *the `md-to-pdf` half is superseded by decision 48* | `build-profile.sh` is existing proof the boundary works. |
| 29 | No agent framework. Deterministic code for the spine; a model **only** for deriving Source configs, scoring relevance, and writing prose | Polling, extraction, hashing, manifests and PDF building must be reproducible, so they should contain no model at all. Hermes was evaluated: its strengths (persistent memory, sandboxes, six chat channels) solve problems this project doesn't have, and its browser and search tools sit behind a paid subscription. Telegram plus voice is roughly 100 lines against the Bot API. |
| 30 | Model access sits behind a small interface with the model named in config | Currently Claude Max 20x, possibly Pro later. Relevance scoring is the volume driver and the tier that would need to drop to a cheap API model. A plan change should be a config edit. |
| 31 | Tier the models: **none** for extraction, cheap for scoring, best for prose | Most extraction is `json.loads` on a JSON-LD block. Cover letters are ~3 a week and can cost real money. |
| 31b | Deployment follows the `pdr.cloud` arrangement: Dokploy **Auto Deploy off**, CI triggers the deploy from its last job once checks are green, over a tailnet the runner joins as a short-lived node | If Dokploy listened to the push itself, tests and deployment would run side by side and a red run would ship anyway. Dokploy has no public address, so the runner joins the tailnet scoped by ACL to the Dokploy host and nothing else. |
| 32 | Access via **Tailscale only** — laptop and phone; nothing on the public internet | Single-user app holding salary floors, rejection history and portal logins. The strongest control is not being reachable, and it costs nothing here. Telegram polls outbound, so no inbound webhook is needed. |
| 33 | Machine credentials in Dokploy/Docker secrets; **portal logins are stored nowhere**, and each portal is entered through its own reset-by-email flow | Different problems. The unattended half of the system needs no secrets at all — the ATS feeds are unauthenticated — and portal logins are only needed at the Send Gate, when a human is present anyway. The email account is already the recovery root of trust for every portal, so a stored password would add a dependency rather than remove one. Better security at zero ergonomic cost. |
| 36 | The Python stack is **Starlette + Jinja2 + uvicorn**, with Application records as **YAML** (`application.yaml`); checks are pytest, mypy strict and ruff, in a plain `.venv` | Settled while building ticket 01, and kept after reconsidering. Starlette is the smallest thing that serves server-rendered templates and has a test client for Seam A; with no JSON API (decision 27) a larger framework would mostly go unused, and Django's ORM, admin and auth are exactly what decisions 7 and 32 do without. YAML is the most forgiving format to edit by hand and holds a dated Status history naturally, which TOML does not. The stack sits behind `create_app(data_dir=, clock=, network=, committer=, model=)` and the tests assert only on rendered output and files on disk, so replacing it later costs the web module, not the suite. |
| 37 | The store is brought up to date **by the service itself at start**, not by an entrypoint script: clone into an empty volume, fast-forward otherwise, and start anyway on a store that cannot be updated. CI runs the **checks on every push**, and gates only the *deployment* on the paths the image is built from. The Dokploy call lives in `deploy/dokploy-deploy.sh`, which CI's deploy job and `deploy/deploy.sh` both run, so a deployment by hand from the dev server and one from a runner cannot drift apart. The Tailscale-only boundary is **verified from the CI runner**, which is a stranger on the public internet | In Python the behaviour sits behind the same tests as everything else, against real repositories, and the credential is handed to git through its environment so it never reaches the volume. A refusing start would turn a GitHub outage into a dashboard outage. Skipping the whole workflow on a prose-only push would also skip the personal data guard, which reads prose. Metered minutes were weighed and found not to bind: the Free plan's 2,000 a month is an order of magnitude more than daily pushes consume. The exposure check is the one thing a machine on the tailnet cannot perform, because from inside it a shut door and an open one look alike. A boundary that is only configured is assumed; one that a stranger tests after every deployment is verified. |
| 38 | The server **pushes after every commit**, synchronously, behind the same Committer the mutations are handed. A push that fails never fails the mutation; it is reported on the dashboard and retried by the next push and at start. **Never forced**: a data repository that has moved ahead is reported and left alone. The deployment's token becomes Contents read *and write*, on `jobs-data` only | Decision 10 counts GitHub as a clone, and it only is one if the server's commits reach it; the restore drill in ticket 05 lost the one Application that had not been pushed by hand. Pushing behind the Committer means nothing that writes has to know about it, and lets the suite assert on it without a network. Synchronous is enough for one user, and bounded by a 30 second patience; a queue would be one more thing to lose. A forced push is the only way this arrangement could destroy history, and with a single writer it is never needed. |
| 39 | The model is a **fifth injected boundary**, `Model.ask(prompt) -> str`, and the real one is the **`claude` command in print mode**, named by `MODEL`. It is given no tools, no settings and no MCP servers. Registration asks it two narrow questions — which links lead onward from this page, and which field and pattern a plain-language rule means — and **verifies the first answer by walking it**: a Source is written only once a posting page has actually been read. The strategy itself is derived by code, never by the model | Decision 30 asked for a small interface with the model named in config; the plan in use is a subscription, which the command line reaches and an API key does not, and shelling out is the boundary decision 28 already trusts. A prompt carries text from pages anyone can write, so a model that can do nothing but answer is the control against an instruction planted in a careers page. Asking for a pattern rather than for the postings keeps what the model decides small enough to read in the config and correct by hand, and checking it against the live pages is what lets registration refuse at once instead of creating a Source that never returns anything. |
| 40 | A Posting is **`postings/<source>/<name>.yaml`**, and the name is made from its **identity alone**: a readable slug of what identified it and a short hash. Identity is the published identifier, otherwise the canonical URL, otherwise a hash over company, role and location. The URL only counts as a Posting's own when the page was **reached through the hop chain and carries no other Posting**. Two different Postings in one walk resolving to one identity are **never merged quietly**: the first is kept and the poll reports the other. A poll refreshes the fields it owns and leaves every other field in the file alone. How the last poll went is **`polls/<source>.yaml`**, which is also what the schedule reads | The folder is the scoping to the Source, so the same position through two Sources is two files with no rule needed. A name made from identity means finding a Posting again is a path, not a search, and a reworded role keeps its file. A listing's URL is shared by everything on it and would merge them all into one, which is the silent loss the spec warns about; an identifier a site repeats across postings would do the same, and that cannot be told from a genuine duplicate, so it is made loud instead of guessed at. Tickets 12 and 13 write first-shown, dismissed and pursued into the same file, so a poll must not own the whole of it. The poll record sits apart from `sources/<name>.yaml` because that file is a human's to edit, and it is on disk rather than in memory so a redeploy neither skips a day nor polls everything again. |
| 41 | The proposal list is made **each time it is read**, and reading it is what **shows** a Posting: whatever the cap lets through has `first_shown` written on its file and committed. The cap counts Postings **first shown on one day**, so dismissing makes no room and the list itself can be longer than the cap. The cap, the age-out period and the global rules are **`proposals.yaml` in the data directory**. What the rules remove, what aged out and what expired are **derived, never written**; only `first_shown` and `dismissed` are, once each. The rules sit behind **`Relevance.judge(posting) -> Verdict`**, a yes or no with a reason | Decision 19 capped a digest at five a day, and a cap on first showings is the reading under which a held-back Posting is one without a first-shown date, as decision 20 needs. The rules say where and what one is looking for, which is personal, so they live with the data and not in the environment. Judging on every read keeps the filter auditable in the useful direction: relaxing a rule that was too aggressive brings back what it removed, and no stale verdict has to be migrated when a scorer replaces the rules. |
| 42 | Shared Documents are **`documents/store/<sha256><extension>`**, and **`documents/shared.yaml`** maps the filename a Document is linked in under to the stored file that holds its bytes. A new Application gets a **relative symlink** per entry, made when it is created and never moved afterwards: adding a new version under a name that is taken changes what the *next* Application gets, and the ones that exist keep what they have. Nothing is ever removed from the store. An Application is **not created** while `shared.yaml` cannot be read or names bytes the store does not hold | A relative link is the only kind that survives a clone to another path, and git stores it as a link. The extension stays on the stored file so the store itself can be opened from a file manager, at the price of one more copy should the same bytes ever be added under two extensions. The mapping is a file rather than a convention so the set can be edited by hand, and so the name in the folder is free of the name the file arrived under. Existing links are left alone because an Application may already have been sent with what it links to; deciding that is the Send Gate's, with the Manifest. The store is never cleaned for the same reason: what an old link points at must stay. A folder scaffolded with a dangling or a missing link looks complete and is not, so that is refused loudly instead. |
| 43 | The Pursue Gate is **one form post of everything ticked**, and each tick is **one commit**: the scaffolded Application folder and the `pursued` moment on the Posting's file together. The Posting is stored in the folder as **`posting.yaml`, a copy of the kept file as it stood when ticked**, never a link, and `posting.yaml` joins `application.yaml` as a filename no shared Document may take. The folder is dated by the **day it was ticked** and made by the same scaffolding as one created by hand. The `pursued` mark is written **last**: if it cannot be, the folder is removed again; if the folder cannot be made, the Posting stays proposed. Only a Posting that **was shown** can be ticked; one the cap still holds back cannot. One tick that is refused does not stop the others; one that **cannot be committed** does, and says what is left on disk | A copy is the point of story 34: the kept file is the poll's to refresh and may one day be pruned, while what was advertised on the day of the decision must stay. Marking last means the failure that is left over is never a Posting that vanished from the list with no Application to show for it. One commit a tick keeps the history readable as decisions, and one code path for scaffolding is what makes a ticked folder indistinguishable from a hand-made one. Nothing here touches the network, so the slice ends with no way to transmit anything to an employer (ADR 0001). |
| 44 | The `claude` command **ships in the image**, signed in by a **`claude setup-token` token held as a Dokploy secret** (`CLAUDE_CODE_OAUTH_TOKEN`). The API Model is deferred, not rejected | Ticket 15 had to put a second credential into a deployment that held one, and the two ways of doing it were weighed against a built image rather than on paper. The command turned out to cost far less than assumed: a single glibc-linked binary, no node runtime, and `ClaudeCli` unchanged — 239 MB of image and a token re-minted once a year, against a Console account and a payment method that do not exist for a question asked twice per Source. Decision 39's reasoning holds: the plan in use is a subscription the command line reaches and an API key does not, and it is Max 20x, so the headroom is the one decision 30 assumed. The session credential was ruled out by measurement, not taste — its access token lives about a day and its refresh token about eighteen, both rotated in place, so a copy mounted as a secret would work for a day and then fail silently, and registration is rare enough (decision 13) that it would go stale precisely because it is seldom asked. Decision 30 keeps its promise: relevance scoring, the volume driver, is a second Model behind the same interface and a config edit |
| 45 | Rendering is a **second method on the Network boundary**, `render(url, ready)`, and the real one is **Chromium driven by Playwright**, started for one page and closed after it. `ready` is asked of what the page shows until it says yes or the patience runs out: a hop waits for a link its pattern matches, a posting page for a Posting. A listing whose markup yields nothing is retried rendered; posting pages at the end of a chain are not retried one by one | The walk knows what it rendered a page for, the browser does not, so the question travels with the request and the browser never sleeps a fixed time. One process per page costs about a second and leaves nothing to supervise or leak in a service that renders a few pages a day. Retrying every empty posting page would turn one redesign into fifty browser starts. Chromium runs without its sandbox, as Playwright starts it, which the container and the unprivileged user stand in for. |
| 46 | The proposal list is **not capped unless `proposals.yaml` sets `cap:`**, and each proposal gives **everything kept of its Posting** beside it, the whole description behind its extract. Takes back the five a day of decision 19; the reasons and the inspectable rejections of 19 stand | Settled by using it, as ticket 12 left it to be. With a handful of Sources the first polls bring twenty Postings, and a cap that shows five of them a day hides what there is to decide on rather than protecting attention; held back, a Posting with a near Deadline can pass it unseen. The cap was against a digest that gets muted, and this list is pulled, not pushed. It stays a setting for the day the volume makes it wanted. Deciding took opening each posting page, because the list gave an extract and two facts. |
| 47 | There are **two Strategies, structured record and selectors**; a model is never one. This amends decisions 14 and 39. At registration, where no structured record is found, the model is asked a third narrow question — which CSS selector holds each field on this page, shown as markup reduced to its tags, ids and classes — and the answer is **verified by code on every page the exploration reached**: the required fields must be there on each, and the role must not be the same on all of them. One retry, told what went wrong; then registration refuses. The strategy is still *chosen* by code, by trying in order. Selectors are CSS, read with `beautifulsoup4` and `soupsieve`, kept in the Source config and editable by hand; the company may be a literal beside them. At a poll a page whose selectors find no role has failed, which makes the Source unhealthy at once. Re-derivation tries the selectors it has before asking for new ones | Decision 14 named a model as a third way of reading a page, and a poll runs the Strategy its config names, so a Source frozen to it would have asked a model on every page of every poll — against story 14, decisions 29 and 31, and ADR 0003, which already said the agent writes a config that is then run as deterministic code. Selectors are what that config holds when a site publishes no record. Code cannot know which element is the role, so the model proposes; but what it decides stays as small as a hop pattern, readable in the file and checked against live pages before anything is written. The sameness check is there because a selector that hits the site's header on every page is the ordinary way this goes wrong without an error. CSS because it can be written and tried in a browser's tools; the pure-Python library because a poll reads dozens of pages, not thousands, and a compiled wheel is one more thing a Python upgrade waits for. Keeping working selectors at Re-derivation stops a model's rewording from overwriting a hand correction. |
| 48 | A PDF is built from Markdown **by the Chromium already in the image**: Markdown to HTML in Python, then printed through Playwright. Supersedes the `md-to-pdf` half of decision 28. The engine ships a neutral template and stylesheet; ones in the data directory replace them | `md-to-pdf` is itself Markdown to HTML to headless Chromium, and the image has Chromium since decision 45 and no node. The same kind of output for one Python library instead of a second runtime. The resume is built the same way from one Markdown file and one stylesheet, so its stylesheet can serve the Letter. |
| 49 | A model writes only the **body** of a Letter, subject line through closing formula, and returns it **whole, as text, with no tools**; code computes the difference. Sender, the employer's address, the date and the signature come from a template and the Application record | A Letter is under a page, so sending it whole costs nothing, and a model that reads a Posting anyone could have written keeps being able to do nothing but answer (decision 39). An address or a date is a fact, and a fact a model can rewrite is the wrong figure decision 22 is about. The cut was taken as a default and is open again after the first real Letter. |
| 50 | A Revision **takes effect when accepted and not before**, all of it or none, and there is at most one waiting per Letter. The difference is always against the Letter as it stands. This makes decision 22's "what was last seen" exact | It is what Re-derivation already does. Held apart from the Letter file, a proposal cannot be mistaken for the Letter, and what stands on disk is by definition what was last accepted. Accepting part of one would leave a text that neither the user nor the model wrote as a whole. |
| 51 | The Conversation is **stored in the Application folder and committed**, unlike a Registration, and keeps the text of the waiting Revision only. The PDF is **never committed** before the Send Gate | A deploy restarts the service, which would otherwise end a sitting, and why a sentence reads as it does is answered by the message that asked for it. A PDF per accepted Revision would put dozens of binaries per Letter into the repository ADR 0002 measured, and the Manifest needs only the one that is sent. |
| 52 | The pages are **designed for a phone first**: one column, the pages along the bottom edge, a list as an entry each, controls a finger can hit, and columns only from a wider screen on. The look is a desk for correspondence: the grey of recycled paper as the ground, white sheets on it, royal blue ink, red pencil for what is struck out, Barlow for everything and Vollkorn for the Letter alone. This replaces decision 27's stylesheet: only the status colours are kept, and every style is in the one file | Proposals are ticked and a Revision is read on a phone more often than at a desk, and there every page scrolled sideways, its buttons hung off the screen and its tables dropped the Role. A stylesheet that may not change cannot be made to fit, and the styles added beside it for every page since were the same rule being got around. |
| 53 | Specs and tickets are **GitHub issues**: a spec is an issue, its tickets are sub-issues with native dependencies, triage state is a label and done is closed. The tickets once written as files leave the tree | The tickets were files in the tree because git was the only transport; that tied them to the code's history and to whoever may read it. As issues they stay where the repository is, and the tree holds the engine alone, which is what lets one repository be shared and later opened. |
| 54 | A Posting found by hand **becomes an Application directly**, from one page that is **always confirmed**: opened with a title, a link and a text it shows the form filled in and creates nothing until Create. With a link or a text the Application holds a **Posting brought in by hand**, in the form of a kept Posting and committed with it; it belongs to no Source and is never polled, proposed or aged out. The server **fetches nothing it was handed, on any site**, which widens decision 16 from five sites to all of them for what is brought in by hand | The Postings picked by hand are the ones the applicant is surest about, and registering a Source, polling it and ticking the Proposal is three pages for one Posting that fail outright behind a login. The sites this is most useful for are the ones the server must not open, so everything comes from the applicant's own browser, and a share made by mistake must not land in the store. Bringing one in is the applicant's decision, which is all ADR 0001's first gate asks. |
| 55 | The company and role are **guessed from the page's title by plain code**: the site's own name dropped from the end, the title split on its separators, and "role at company" (or "bei") and "company is hiring role" read; what fits no shape is the role, with the company left empty | Decision 29: no model where code will do. The guess is only a proposal in two fields to correct, nothing depends on it, and a title that is really a slogan loses nothing. |
| 56 | A Posting brought in by hand **without its text may be given it once**, whatever its Application's Status, from a field on the Application's page that is there only while it has none; saving it is one commit of the Posting's file, and from then on the text is fixed like the rest. The same link coming in again, **on opening the page that creates an Application as well as on Create**, leads to that field filled in with the text it brought and saves nothing; while the Posting has a text, it leads to the Application and the text is dropped | A job shared from the LinkedIn app arrives without its description, and the narrow exception is what lets it get one at the desk without a second Application. Once is enough because a later share is the same page, and a Posting that changes after it was brought in would no longer be what was decided on. The check moved onto opening the page so that the bookmark button on a job already brought in is one click and Save. |
